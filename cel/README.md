# cel

Package `github.com/vulnetix/config-schemas/cel` compiles and evaluates the [CEL](https://cel.dev) expressions in Vulnetix config documents: the `when` of quality gate, jail, prioritisation and suppression rules, package firewall and AI firewall rules, factory trigger conditions, and detection rule feed selectors. Every expression must return `bool`.

The vulnetix CLI and the config engine in vdb-site both use this package and both run the golden vectors in `testdata/vectors`, so a rule gives the same answer in CI as on the server.

## Use from Go

```go
prg, err := cel.Compile(cel.ContextFinding, `severity == 'critical' && (kev || reachable)`)
if err != nil {
	// *cel.Error: Code is one of the codes below; Issues carry line and column.
}
ok, err := prg.Eval(cel.Finding{Severity: "critical", KEV: true})
```

Compile once and reuse the `Program`; it is safe for concurrent use. `cel.Check(ctx, expr)` is Compile for plan and validate, returning only the error. `prg.Cost()` is the estimated cost range.

A runtime that evaluates stored rules uses the cached helpers instead, so each distinct expression is compiled once per process:

```go
ok, err := cel.EvalFinding(rule.When, cel.Finding{Severity: "high", KEV: true})
// also EvalPackage, EvalRequest, EvalEvent, EvalCVE, and Eval for any Input
```

They share one `cel.Cache` of up to 4096 programs. A compile error is cached too, so a stored rule that does not compile fails the same way, cheaply, every time; `cel.NewCache(n)` gives a caller its own.

What a runtime does when a rule errors is its own business rule, and each one documents it: the jail and quality gate fail closed (the rule matches), a suppression or prioritisation rule fails open (it does not match), and the firewalls log and skip the rule.

Each context has its own input struct (`Finding`, `Package`, `Request`, `Event`, `CVE`), and `Eval` refuses an input of another context. Every struct has a `Now` field; leave it zero to evaluate at the current time, or set it to get the same answer on every run. Derived variables (marked in the tables) are computed from the other fields and have no field of their own.

## Errors

| Code | When |
|---|---|
| `length` | The expression is longer than the limit. |
| `syntax` | It does not parse. |
| `type` | It does not type-check: an unknown variable, a variable from another context, or a comparison between the wrong types. |
| `result_type` | It type-checks to something other than `bool`. |
| `cost` | Its estimated cost at compile time, or its actual cost at evaluation, exceeds the limit. |
| `context` | An unknown context, or an input of the wrong context. |
| `input` | The input exceeds a variable's bound. |
| `eval` | Evaluation failed, for example an invalid purl passed to `matchesPurl`. |

The codes are stable across cel-go versions; the messages are not. Line and column are 1-based.

## How cost is bounded

CEL charges every operation a cost. At compile time this package estimates the worst case by assuming every string and list is at the bound in the tables below, and refuses an expression whose estimate exceeds the limit. At evaluation it refuses an input past a bound, and stops evaluation that goes past the limit. The bounds are therefore a contract with callers: a caller with more data than a bound allows sends the first part and says so (`paths` and `pathsTruncated` on an event).

A single `exists` or `all` over a list costs a few hundred thousand at most. A comprehension nested inside another over the same list, or a regex over several long strings joined together, usually does not fit.

`cvss >= 7` type-checks: comparisons between ints and doubles are enabled. Equality is not, so write `cvss == 7.0`. The cel-go extension libraries (strings, math, lists) are not loaded, because their functions carry no cost estimates.

## Golden vectors

`testdata/vectors/<context>.yaml` holds plain-data cases: an expression, an input keyed by variable name, and either `want` (the result) or `error` (the code), with an optional `at` for the first issue's position. Variables an input leaves out take their zero value. The vectors are embedded, so an importer runs exactly the ones its pinned version was tested with, through its own evaluation path:

```go
for _, err := range cel.RunVectors(myRuntime.Evaluate) { // func(expr string, in cel.Input) (bool, error)
	t.Error(err)
}
```

`v.Run(ctx)` checks one vector with Compile and Eval; `v.RunWith(ctx, eval)` checks it through any evaluator.

### Functions

Available in every context, alongside the [CEL standard library](https://github.com/google/cel-spec/blob/master/doc/langdef.md#list-of-standard-definitions).

| Function | Description |
|---|---|
| `string.glob(pattern string) bool` | Glob match over the whole string. `*` is any run of characters except `/`, `**` is any run including `/`, `**/` is zero or more directories, `?` is one character except `/`. Everything else is literal. The same dialect as factory trigger conditions. |
| `string.matchesPurl(pattern string) bool` | Package URL match. The pattern is a purl: without a version it matches every version, with one it matches that version only. A pattern whose name ends in `/*` or `:*` matches every package under that namespace, as package firewall allow entries do: `pkg:npm/@acme/*` covers `pkg:npm/@acme/tool@1.0.0` but not `pkg:npm/@acme-evil/tool`. Qualifiers and subpaths are ignored. Names compare as written. An invalid purl or pattern is an evaluation error. |
| `semverCompare(a string, b string) int` | -1, 0 or 1 as `a` is lower than, equal to or higher than `b` in semantic version order. Precedence follows SemVer 2.0.0: pre-releases rank below the release and build metadata is ignored. A leading `v` is optional; the shorthands `1` and `1.2` are not versions. A value that is not a semantic version is an evaluation error; guard with `isSemver`. |
| `isSemver(v string) bool` | Whether `v` is a semantic version, with or without a leading `v`. |

### Limits

| Limit | Value |
|---|---|
| Expression length | 4096 bytes |
| Estimated cost, checked at plan | 1000000 |
| Actual cost, checked at evaluation | 1000000 |

The estimate assumes every string and list is at its bound in the tables above, and evaluation refuses an input past a bound, so an expression that passes plan cannot exceed the limit when it runs. A single `exists` or `all` over a list is well inside it; a comprehension nested inside another over the same list usually is not.
